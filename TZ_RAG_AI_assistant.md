# ТЗ: AI-ассистент по документам (RAG-платформа)

## 1. Цель проекта

Учебно-портфолийный проект, цель которого — не просто "запустить чат с LLM", а построить полноценный продукт: обработка документов, поиск по смыслу (RAG), несколько интерфейсов (веб + Telegram), авторизация, очереди, деплой, тесты. Проект должен закрыть пробел в коммерческом опыте и продемонстрировать на собеседованиях владение современным стеком.

## 2. Функциональные требования (что должно делать приложение)

1. Пользователь регистрируется и авторизуется (email/пароль + OAuth через Google).
2. Пользователь создаёт "базу знаний" (workspace) и загружает в неё документы: PDF, DOCX, TXT, Markdown, а также ссылки на веб-страницы.
3. Система автоматически обрабатывает документ: извлекает текст, режет на чанки, считает эмбеддинги, сохраняет в векторную БД. Обработка идёт в фоне, пользователь видит статус (в очереди / обрабатывается / готово / ошибка).
4. Пользователь задаёт вопрос в чате (веб-интерфейс) по своей базе знаний и получает ответ, сгенерированный LLM на основе найденных релевантных фрагментов, с указанием источников (какой документ и какой фрагмент использован).
5. Ответ стримится по частям (как в ChatGPT), а не приходит одним блоком.
6. История диалогов сохраняется, можно вернуться к прошлому чату.
7. Тот же функционал доступен через Telegram-бота: пользователь привязывает аккаунт и общается с базой знаний прямо в мессенджере.
8. Реализовано разграничение доступа: пользователь видит только свои базы знаний (мультитенантность на уровне данных).
9. (Опционально, если будет время) Простой агентный режим: LLM сама решает, искать ответ в базе знаний или сходить в веб-поиск, если локальных данных недостаточно.
10. (Опционально) Лимиты использования — например, N бесплатных вопросов в день, дальше — заглушка "оформите подписку" (реальная оплата не обязательна, важна сама механика лимитов).

## 3. Нефункциональные требования

- Backend: Python, FastAPI, полностью асинхронный код (async/await везде, включая работу с БД).
- База данных: PostgreSQL + асинхронный SQLAlchemy 2.0 + Alembic для миграций.
- Векторный поиск: расширение pgvector в том же Postgres (не поднимать отдельную БД, чтобы не усложнять инфраструктуру раньше времени).
- Очереди/фон: Celery или ARQ + Redis как брокер.
- LLM/эмбеддинги: любой провайдер через единый API (например, OpenRouter или OpenAI SDK), логика взаимодействия с LLM должна быть спрятана за собственным интерфейсом (чтобы провайдера можно было заменить, не трогая остальной код).
- Авторизация: JWT (access + refresh токены), OAuth2 через Google.
- Инфраструктура: Docker + docker-compose для локального окружения (минимум: api, db, redis, worker).
- CI: GitHub Actions — прогон тестов и линтеров при каждом пуше.
- Тесты: pytest, покрытие ключевой бизнес-логики (обработка документов, RAG-пайплайн, авторизация), внешние вызовы LLM в тестах мокаются.
- Код: типизация (mypy), линтер (ruff), понятная слоистая архитектура (роутеры → сервисы → репозитории), никакой бизнес-логики в роутерах.
- Логирование ошибок: хотя бы базовая интеграция с Sentry или структурированные логи.

## 5. Этапы и мелкие шаги реализации

Каждый этап рассчитан так, чтобы после его завершения было что закоммитить и проверить руками. Не переходи к следующему этапу, пока текущий не работает целиком.

### Этап 0. Подготовка окружения
- [+] Создать репозиторий, настроить `.gitignore`, `pyproject.toml`/`requirements.txt`
- [+] Настроить `ruff` и `mypy`, добавить pre-commit хуки
- [+] Поднять `docker-compose.yml` с сервисами: `db` (Postgres с pgvector), `redis`
- [+] Написать `Dockerfile` для приложения (пока пустого FastAPI со `/health`)
- [+] Проверить, что `docker-compose up` поднимает всё и `/health` отвечает 200

### Этап 1. Данные и авторизация
- [+] Спроектировать модели: `User`, `Workspace`, `Document`, `Chunk`, `Chat`, `Message`
- [+] Настроить асинхронный SQLAlchemy + первую Alembic-миграцию
- [+] Реализовать регистрацию/логин по email+паролю, хэширование паролей (passlib/argon2)
- [+] Реализовать выдачу JWT access+refresh токенов, эндпоинт refresh
- [ ] Добавить OAuth2 через Google (можно на этом этапе, можно вернуться позже)
- [+] Написать тесты на регистрацию, логин, доступ к защищённым эндпоинтам без токена (должен быть 401)

### Этап 2. Workspaces и загрузка документов
- [+] CRUD для `Workspace` (создание, список, удаление) с проверкой, что пользователь видит только свои
- [ ] Эндпоинт загрузки файла (PDF/DOCX/TXT/MD), сохранение файла (локально или S3-совместимое хранилище, можно MinIO в docker-compose)
- [ ] Модель `Document` со статусом (`pending`, `processing`, `ready`, `failed`)
- [ ] Тесты: загрузка файла создаёт запись со статусом `pending`

### Этап 3. Фоновая обработка документов
- [ ] Подключить Celery/ARQ + Redis, поднять worker в docker-compose
- [ ] Задача: извлечь текст из файла (использовать библиотеки под каждый формат: `pypdf`, `python-docx` и т.д.)
- [ ] Разбить текст на чанки (фиксированный размер с перекрытием — начать просто, без хитрой семантической сегментации)
- [ ] Посчитать эмбеддинги для чанков через выбранного провайдера
- [ ] Сохранить чанки с эмбеддингами в таблицу с `pgvector`-колонкой
- [ ] По завершении обновить статус документа на `ready` (или `failed` с текстом ошибки)
- [ ] Тесты: замокать вызов эмбеддингов, проверить, что после задачи статус меняется и чанки появляются в БД

### Этап 4. RAG-пайплайн и чат
- [ ] Эндпоинт вопроса: принимает вопрос + workspace_id
- [ ] Векторный поиск top-k релевантных чанков по косинусному сходству
- [ ] Сборка промпта: системная инструкция + найденные чанки + вопрос пользователя
- [ ] Вызов LLM, стриминг ответа через SSE или WebSocket
- [ ] Сохранение вопроса и ответа в историю чата, с привязкой к использованным источникам
- [ ] Тесты: замокать LLM-вызов, проверить сборку промпта и сохранение истории

### Этап 5. Веб-интерфейс
- [ ] Минимальный SPA (React) или HTMX-страница: список workspaces, загрузка файла, окно чата
- [ ] Отображение статуса обработки документа (поллинг или WebSocket)
- [ ] Отображение стриминга ответа в реальном времени
- [ ] Показ источников рядом с ответом (кликабельные ссылки на документ/фрагмент)

### Этап 6. Telegram-бот
- [ ] Бот на aiogram: команда привязки аккаунта (например, через одноразовый код, сгенерированный в вебе)
- [ ] Выбор активного workspace через inline-кнопки
- [ ] Отправка вопроса — бот дергает тот же backend API, что и веб
- [ ] Отображение ответа (без стриминга, либо с редактированием сообщения по мере генерации)

### Этап 7. Полировка и то, что отличает pet-проект от продукта
- [ ] Rate limiting на уровне API (например, через `slowapi` или Nginx)
- [ ] Лимиты на количество вопросов/документов на пользователя
- [ ] Обработка ошибок LLM-провайдера (таймауты, ретраи с backoff)
- [ ] Базовый мониторинг ошибок (Sentry) и логирование ключевых событий
- [ ] README с архитектурной схемой и инструкцией по запуску

### Этап 8. CI/CD и деплой
- [ ] GitHub Actions: workflow с запуском линтеров и тестов на каждый PR
- [ ] Отдельный workflow сборки Docker-образа и (опционально) деплоя на VPS
- [ ] Nginx как reverse proxy перед FastAPI, настройка HTTPS (Let's Encrypt)
- [ ] Развернуть рабочую версию на реальном сервере, чтобы был живой демо-линк

### Этап 9 (опционально). Агент и монетизация
- [ ] Function calling: LLM решает, искать ли ответ в базе или уточнить у пользователя/сходить в веб-поиск
- [ ] Подписка/лимиты через Stripe или заглушку оплаты
- [ ] Аналитика использования (сколько вопросов, какие документы популярны)

## 6. Критерии успешного завершения

- Пользователь может зарегистрироваться, загрузить документ, получить статус его обработки и задать по нему вопрос — и в вебе, и в Telegram.
- Ответы генерируются с опорой на реальные фрагменты документов, а не "из головы" модели.
- Проект поднимается одной командой (`docker-compose up`) на чистой машине.
- Есть тесты, которые проходят в CI при каждом пуше.
- Есть README, по которому сторонний разработчик поймёт архитектуру за 10 минут.

## 7. Как использовать этот документ

Двигайся строго по этапам сверху вниз, отмечай чекбоксы. Если застреваешь на каком-то шаге дольше пары дней — это сигнал упростить подзадачу, а не пропускать её.
